# X-Cyber-LRC-Hub 技术架构与开发规范文档

> **组织**：`x-cyber-space`  
> **项目名**：`x-cyber-lrc-hub`  
> **开源协议**：`GNU Affero General Public License v3.0 (AGPL-3.0)`

---

## 1. 项目定位与使命

`x-cyber-lrc-hub` 是一个专为音乐爱好者、自建 NAS 玩家及极客开发者打造的**轻量级、自建式（Self-Hosted）、兼容 LRCLIB 标准协议的歌词聚合与中转服务**。

- **去中心化与隐私安全**：服务运行于用户本地计算机、NAS 或软路由上，所有检索流量均通过用户自身的家庭网络发起，绝无中心化服务器监控与封禁风险。
- **协议标准化**：对外提供与 [LRCLIB](https://lrclib.net/) **读取侧**对齐的公开 REST API（`/api/get`、`/api/get/{id}`、`/api/search`），使得任何支持 LRCLIB 的现代播放器（如 ZZMusicPlayer、Symfonium 等）均可接入。响应字段、空值语义与错误响应体均对 `lrclib.net` 实测核对。
  - 未实现写入侧（`POST /api/request-challenge`、`POST /api/publish`）—— 本项目是只读的聚合代理，不承载发布流程。
- **责任隔离**：作为独立的通用开源抓取代理，与任何特定商业播放器无从属绑定关系。

## 3. LRCLIB 接口规范（读取侧对齐）

服务默认监听 `0.0.0.0:3300`，需完整实现以下端点：

### 3.1 核心获取接口：`GET /api/get`
用于播放器播放单曲时的精准匹配与获取。

- **Query 参数**：
  - `track_name` (string, 必需): 歌曲名称
  - `artist_name` (string, 必需): 歌手名称
  - `album_name` (string, 可选): 专辑名称
  - `duration` (integer/float, 可选): 歌曲时长（秒）

- **返回状态码**：
  - `200 OK`：成功匹配到歌词
  - `400 Bad Request`：缺少必需参数，返回 `text/plain`，内容为 ``Failed to deserialize query string: missing field `track_name` ``
  - `404 Not Found`：未找到歌词，返回 `{"message":"Failed to find specified track","name":"TrackNotFound","statusCode":404}`
  - `405 Method Not Allowed`：空响应体，且不带 `Content-Type`
  - `503 Service Unavailable`：所有提供方均失败时返回 `ServerOverloaded`，避免把上游故障伪装成"没有这首歌"

- **返回 JSON 结构**（字段与 `lrclib.net` 逐字节一致，共 10 个）：
```json
{
  "id": 10001,
  "name": "七里香",
  "trackName": "七里香",
  "artistName": "周杰伦",
  "albumName": "七里香",
  "duration": 299,
  "instrumental": false,
  "plainLyrics": "窗外的麻雀 在电线杆上多嘴...",
  "syncedLyrics": "[00:00.00] 作词 : 方文山\n[00:02.00] 作曲 : 周杰伦\n[00:18.50]窗外的麻雀 在电线杆上多嘴\n[00:22.80]你说这一句 很有夏天的感觉...",
  "lyricsfile": "version: '1.0'\nmetadata:\n  title: 七里香\n..."
}
```

`plainLyrics` / `syncedLyrics` / `lyricsfile` 在缺失时输出 JSON `null`，而不是空字符串；`name` 恒定存在。

### 3.2 按 ID 获取：`GET /api/get/{id}`
返回对应 ID 的缓存记录；不存在（或已过期）时返回与 3.1 相同的 404。

### 3.3 模糊搜索接口：`GET /api/search`
用于用户在 UI 中手动搜索或未命中精确匹配时的候选列表。

- **Query 参数**：
  - `q` (string, 可选): 综合搜索关键词
  - `track_name` (string, 可选): 歌曲名过滤
  - `artist_name` (string, 可选): 歌手过滤
  - `album_name` (string, 可选): 专辑过滤

- **返回 JSON 结构**：
  - 返回对象数组 `[ { ... }, { ... } ]`，每个对象格式同上，歌词内联，最多 20 条。
  - 参数全为空、或检索无结果时，均返回 `[]` 与 `200`（而不是 404）。

## 4. 多源抓取与两级匹配策略

> **本节经对 `lrclib.net` 实测校准，不是设计猜想。** 改动匹配规则前请先探测真实端点。

### 4.1 抓取平台适配器
1. **网易云音乐 (NetEase)**:
   - 搜索: `https://music.163.com/api/search/get/web?csrf_token=&type=1&limit=5&s={query}`
   - 歌词: `https://music.163.com/api/song/lyric?os=pc&id={songId}&lv=-1&kv=-1&tv=-1`
2. **QQ音乐 (QQ Music)**:
   - 搜索: QQ 音乐客户端精简搜索接口（返回 `mid` / `songmid`）
   - 歌词: QQ 音乐公开 LRC 解密/Base64 解码接口
3. **酷狗音乐 (Kugou)**:
   - 搜索: Kugou Song Search 接口（获取 `FileHash`）
   - 歌词: Kugou Search Lyrics 接口获取 `id` 与 `accesskey`，拉取 Base64 编码的歌词
4. **酷我音乐 (Kuwo)**:
   - 搜索: Kuwo 搜索 API（获取 `rid`）
   - 歌词: Kuwo 歌词接口获取时间轴 LRC

### 4.2 `GET /api/get`：确定性硬过滤（`internal/matching`）

**打分模型不参与这里的取舍。** 加法模型会让满分歌名（45）掩盖完全不符的歌手（0）：请求 `童话 / 光良` 时，候选 `童话 / 王菲` 仍能拿到 45 分并越过原 40 分门槛，从而返回另一位歌手的歌词。歌手不符是**硬矛盾**，不是扣分项。

第 1 级 —— 与 lrclib.net 同构：

1. **归一化**：转小写、剥离括号修饰词、折叠空白。因此 `七里香 (Live)` 与 `七里香` 属于同一身份，`Wildest Dreams (Taylor's Version)` 也能命中原版记录。
2. **硬条件**：歌名归一化后必须相等；歌手与专辑**仅在请求提供时**才要求相等。
3. **时长窗口**：请求带 `duration` 时，取 ±3 秒内**最接近**的记录。实测：220s 的记录对 220/221/222s 的请求均命中；225s 会改投更近的 226s 记录；230s 未命中。

第 2 级 —— 受控放宽（仍为零模型依赖的确定性规则）：

1. **多歌手集合匹配** —— 请求 `周杰伦` 可匹配平台署名 `周杰伦 / 费玉清`。按 ` / ` ` & ` `、` `,` `feat.` 等分隔符切分后比较集合。
2. **时长窗口放宽到 ±5 秒**。
3. **平台标题后缀** —— 请求 `晴天` 可匹配 `晴天 现场版`；要求候选更长，且请求至少 2 个字符（否则 `红` 会吞掉 `红玫瑰`）。
4. **不再要求专辑相等** —— 专辑只在第 1 级硬过滤。LRCLIB 的专辑列是它自己规整过的数据，而我们抓取的平台专辑名与用户文件标签经常对不上（版本后缀、简繁差异、再版合集）。

两级都不命中 → `404`。**绝不退而求其次返回"分数最高"的候选。**

### 4.3 `GET /api/search`：加权排序（`internal/scoring`）

这里才使用加权打分做**排序**（满分 100 分），排序后保留 40 分下限：

1. **歌名契合度 (最高 45 分)**：
   - 文本清洗规则：转小写，去除括号及修饰词（如 `(Live)`、`[Remix]`、`（伴奏）`、`【超清】`），去除非字母数字汉字字符。
   - 判定标准：
     - 完全一致：`45 分`
     - 包含关系（子串）：`38 分`
     - 相似度计算（Bigram / Jaccard 相似度）：`similarity * 45`
2. **歌手契合度 (最高 30 分)**：
   - 判定标准：
     - 目标未知（如 "未知歌手"、"Unknown"）：给予中立基础分 `20 分`
     - 完全一致：`30 分`
     - 包含关系：`28 分`
     - 相似度计算：`similarity * 30`
3. **时长契合度 (最高 25 分)**：
   - 规则：
     - 时长绝对误差 $< 1.0\text{s}$：`25 分`
     - 绝对误差 $< 2.0\text{s}$：`24 分`
     - 绝对误差 $< 3.0\text{s}$：`22 分`
     - 绝对误差 $< 5.0\text{s}$：`15 分`
     - 绝对误差 $\ge 5.0\text{s}$：`0 分`

40 分的下限刻意**低于**客户端侧的 60 分线：服务器负责召回，判断留给拥有自身模型、并且有用户看着候选列表的播放器。

> **`matching` 与 `scoring` 必须保持分离。** `matching` 回答"这是不是同一首歌"（闸门），`scoring` 回答"哪个候选更好"（排序）。把两者混在一起，正是上述那类 bug 的来源。

## 5. 本地缓存与性能优化

- **持久化方案**：内嵌 SQLite（纯 Go 实现的 `modernc.org/sqlite`，无需 CGO gcc 工具链）。表名 `lyrics`，一行代表"一首歌的某一个版本"。
- **缓存 Key**：

  ```
  sha256( NormalizeIdentity(title) \0 NormalizeIdentity(artist) \0 时长分桶 )[0:16]
  时长分桶 = round(duration / 2)     // duration 未知时为 -1
  ```

  时长参与分桶，使同一首歌的不同版本（原版 / Live / 伴奏 / DJ 版）各占一行、互不覆盖。分桶宽度 2 秒**有意窄于** ±3 秒的匹配窗口，保证缓存命中不会因分桶本身而被复核拒绝。

  身份只在一处定义（`matching.IdentityKey`），缓存键与结果去重共用它 —— 两处各自计算过一次，结果是搜索结果出现重复行 ID。

- **写入时机**：只有两处，且都必须在真正拿到歌词之后 —— `/api/get` 冷启动命中（用**请求的**身份做键）、`/api/search` 返回的每条结果（用**结果自己的**身份做键）。未命中（404）**不做负缓存**：把上游临时故障固化成"这首歌没有歌词"是错的。
- **命中复核**：命中缓存时必须用**与冷启动完全相同的匹配谓词**重新校验（`cache.Matches`）。否则模糊搜索写进去的结果会直接变成权威答案，服务里所有阈值都会失效。
- **过期**：`-cache-ttl` 控制有效期（默认 30 天，`0` 表示永不过期）。读取时即判定过期，后台每小时（不低于每分钟）清理一次以回收磁盘。
- **并发与持久性**：连接数固定为 1。SQLite 写入本就串行，单次查询是本地小表上的索引查找（微秒级），而请求真正的开销在 4 次外部 HTTP 调用上。启用 `journal_mode=WAL` 与 `synchronous=NORMAL`，把默认回滚日志的「每次提交 fsync」降为「每次 checkpoint 一次 fsync」。

## 6. 极客赛博交互与配置项

启动时在终端打印 Cyberpunk 风格 ASCII Banner（版本号由 `-ldflags -X main.version` 注入）：
```
__  __   ____ y b e r   _      ____    ____     _   _       _     
\ \/ /  / ___|         | |    |  _ \  / ___|   | | | | _   | |__  
 \  /  | |      _____  | |    | |_) || |       | |_| || |  | '_ \ 
 /  \  | |___  |_____| | |___ |  _ < | |___    |  _  || |_ | |_) |
/_/\_\  \____|         |_____||_| \_\ \____|   |_| |_| \___||_.__/ 
             :: X-Cyber Lyrics Hub :: [v1.0.0]
             :: LRCLIB Compatible API Server ::
```

- **命令行参数**：
  - `-port` (int, 默认 3300): 监听端口
  - `-cache` (string, 默认 `./data/lyrics.db`): 缓存文件路径
  - `-cache-ttl` (duration, 默认 `720h`): 缓存有效期；`0` 表示永不过期
  - `-log-level` (string, 默认 `info`): 日志等级，`debug` / `info` / `warn` / `error`

- **日志**：使用 `log/slog` 结构化输出。请求级细节（缓存命中、检索开始）在 `debug`，业务结果与访问日志在 `info`，上游或缓存故障在 `error`。
